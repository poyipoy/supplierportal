# Enterprise ERP/portal in-app URL precedents (Infor OS Portal, SAP Fiori, Dynamics 365, Oracle) and how to reproduce them in self-hosted Laravel 12

Scope note: researched 2026-10-20. Primary vendor docs were preferred; where only community/vendor-partner sources were reachable this is stated next to the claim. Several SAP Help / SAP Community pages returned 403/404 to the fetch tool, so some SAP app-state details rely on search-result summaries of those pages (flagged).

## Q1. Per-product URL anatomy: which parts exist, which are stable/bookmarkable vs session-bound, and why

### Takeaway
All four products split the URL into (a) a host/tenant/environment part, (b) a stable, configuration-level page identifier (Infor LogicalId + program/favorite context, SAP semantic object-action, D365 F&O menu item `mi`, D365 CE `pagetype`+`etn`/`appid`), (c) an optional record key (GUID or business key), and (d) optional context/state. Stability depends on whether (d) is carried inline in the URL (stable, but length-limited and visible) or as a key referencing server-side state (short, but only valid while the server keeps that state). SAP Fiori is the clearest example of the key-reference approach and documents its expiry/cleanup trade-off explicitly.

### Cited Findings

**Infor OS Portal / Ming.le**
- Tenant-scoped path segment `/v2/<TENANT>_<ENV>/` is visible in real Infor-hosted URLs, e.g. the Infor KB link `mingle-portal.us2.prd3.inforcloudsuite.com/v2/CONCIERGE_PRD/` (tenant `CONCIERGE`, environment `PRD`) and the documented trial-mode pattern `https://mingle-portal.inforcloudsuite.com/V2/[TenantID]` — [CFO Solutions blog (Infor partner, ~2024)](https://blog.cfosolutions.com/infor-os-portal-0). (Partner source, not Infor docs; the exact `/v2/<TENANT>_PRD/<UUID>` page-UUID segment from prior research was NOT re-confirmed by any source found in this pass.)
- Infor says the portal must always be opened via the dedicated Infor OS Portal URL provided to the tenant administrator, because loading through it ensures required libraries load — [Infor docs: Accessing Infor OS Portal (2024.x)](https://docs.infor.com/inforos/2024.x/en-us/useradminlib_cloud/inforospug/lsm1436532946807.html) (summary via search result).
- Official link formats: "Links to an application should be done through the format of favorite context (`?favoriteContext=`) or from a link with logicalId (`?logicalId=lid://infor.ln`)." — [Infor OS 2022.x docs: Types of variables](https://docs.infor.com/inforos/2022.x/en-us/useradminlib_onpremises/inforosag_on-premise/kce1636121937696.html)
- Logical ID structure: three parts; the first two form the prefix, the last is the instanceId; multiple installs of the same application share the prefix but differ in instanceId. Examples `lid://infor.homepages.1`, `lid://infor.m3.m3` — [same Infor page](https://docs.infor.com/inforos/2022.x/en-us/useradminlib_onpremises/inforosag_on-premise/kce1636121937696.html)
- "Portable links" contain no hard-coded Logical ID and resolve at runtime using the current default application configuration. Template `{lid://infor.m3}?favoriteContext=CRS610&LogicalId={LogicalId}` resolves to `?favoriteContext=CRS610&LogicalId=lid://infor.m3.m3` (CRS610 is an M3 program ID) — [same Infor page](https://docs.infor.com/inforos/2022.x/en-us/useradminlib_onpremises/inforosag_on-premise/kce1636121937696.html)
- Standard parameters the portal appends to applications opened through the Application Launcher: `LogicalId`, `TenantId`, `inforThemeName`, `inforCurrentLocale`, `inforCurrentLanguage`, `inforTimeZone`; URL templates can use `{TenantId}` e.g. `https://myserver.infor.com/{TenantId}` — [same Infor page](https://docs.infor.com/inforos/2022.x/en-us/useradminlib_onpremises/inforosag_on-premise/kce1636121937696.html)
- Drillback: the Logical ID "is crucial for Infor Ming.le-internal management, but also for functions such as drillback and sharing of page links"; Logical ID must start with `lid://` (example `lid://erpln.mycompany.1`). Drillbacks to applications require four mandatory parameters — Logical ID, View ID, Accounting Entity, ID1 — and "Some View ID parameters have up to 6 further IDs, which are optional." Drillbacks from the portal to dashboards need only the Logical ID; if Ming.le is not present, the drillback action is ignored and an alternative action is triggered — [Infor d/EPM docs: Drillbacks to and from dashboards](https://docs.infor.com/depm/2024.x/en-us/depmolh_cloud/application_studio_cloud/mrh1678908470941.html); [Drillback from a dashboard to an application](https://docs.infor.com/depm/2024.x/en-us/depmolh_cloud/application_studio_cloud/zrq1510174311626.html); [Drillback in Infor Ming.le (BI docs)](https://docs.infor.com/bi/11.0.x/en-us/biasolh/lsm1431935815796.html) (search-result summaries)
- The Ming.le "Share" button is no longer available in the new OS Portal — [CFO Solutions blog](https://blog.cfosolutions.com/infor-os-portal-0)

**SAP Fiori launchpad (FLP)**
- URL form: `{BASE_URL}/sap/bc/ui2/flp?sap-client=...&sap-language=...#{SemanticObject}-{action}` — community "SAP Fiori URL generator" page (non-SAP source) surfaced in search; the semantic object and action separated by a dash appear in the launchpad URL hash — [SAP blog: Cross app navigation in SAP Fiori launchpad](https://blogs.sap.com/2017/06/23/cross-app-navigation-in-sap-fiori-launchpad/) (search summary)
- Semantic object and action are assigned in target mapping, and "the value of the action has no direct influence on the behavior of the application" (i.e. the intent is an indirection layer resolved by the launchpad to an app) — [SAP Learning: SAP Fiori Launchpad Configuration](https://learning.sap.com/learning-journeys/develop-sapui5-applications/configuring-sap-fiori-launchpad_b657c889-9569-4d85-b373-60d19ea33dd6) (search summary)
- Cross-app links are built in code via the CrossApplicationNavigation service (`hrefForExternal` with semantic object, action, params) — [Mindset Consulting: Cross application navigation](https://www.mindsetconsulting.com/cross-application-navigation/) (search summary); `createEmptyAppState` is now deprecated in favour of `createEmptyAppStateAsync` / the `sap.ushell.services.Navigation` service — [SAP Community Q&A](https://community.sap.com/t5/technology-q-a/deprecated-api-call-of-sap-ushell-crossapplicationnavigation/qaq-p/14053064) (community)
- App-state pattern: create an app state, `setData(...)`, `save()`, read its key, put the key in the URL; on return the app reads `sap-iapp-state` from the hash and calls `getAppState(component, key)` to restore — [SAP blog: Restoring Fiori Application State (2017)](https://blogs.sap.com/2017/06/19/restoring-fiori-application-state/); [SAP blog 2020: Cross app navigation … restoring SAPUI5 app data](https://blogs.sap.com/2020/09/22/cross-app-navigation-in-fiori-launchpad-and-restoring-sapui5-app-data-using-crossapplicationnavigation-service/) (search summaries; direct fetch 403)
- "AppState instances are immutable", so the key changes whenever state changes — [SAP blog 2017](https://blogs.sap.com/2017/06/19/restoring-fiori-application-state/) (search summary)
- Storage: "The list of parameters defining an application state is stored on the front-end server, together with a unique key." Shared or bookmarked links to an app state only work while that state still exists on the server — [SAP Help: Cleanup of Expired Application State (NW 7.5)](https://help.sap.com/doc/saphelp_nw75/7.5.5/en-US/ff/b437e68f464478bbd723ca144a22d7/content.htm?no_cache=true)
- Cleanup: run "Cleanup Layered Repository Files (transaction /UIF/CLEAN_LREP)"; parameters "Maximum number of times read: Default value: 0" and "Minimum number of days not accessed: Default value: 365"; results logged under application-log object /UI2/BE; rationale: "To avoid that too much storage space is consumed, you should regularly clean up application states." — [same SAP Help page](https://help.sap.com/doc/saphelp_nw75/7.5.5/en-US/ff/b437e68f464478bbd723ca144a22d7/content.htm?no_cache=true); also [UI add-on 2.0 version](https://help.sap.com/docs/UI_ADD-ON_FOR_SAP_NETWEAVER_20/17ae0e97e0fc424a9c368f350c0ba6bd/ffb437e68f464478bbd723ca144a22d7.html)
- Launchpad parameter `APPSTATE_TRANSIENT`: by default state is kept in a temporary browser area — only same browser and same session — so it cannot be reproduced in other browsers/devices; a persistent configuration is required for sharing — [SAP Community: Configuration of Fiori app state for sharing](https://community.sap.com/t5/technology-blog-posts-by-sap/configuration-of-fiori-app-state-for-sharing/ba-p/14240470) (search summary; direct fetch 403)
- SAP KBA 3260742 "Fiori appstate is not persisted across browser sessions": bookmarking or saving as tile opens the app in its base state without filters; after launchpad timeout/logout a previous state may not reappear — [SAP KBA 3260742](https://userapps.support.sap.com/sap/support/knowledge/en/3260742) (search summary)
- For extended apps, custom state can be declared with a "permanent" lifecycle that survives the session (for bookmarks/e-mailed links) — [SAP Help: Custom State Handling for Extended Apps](https://help.sap.com/docs/SAPUI5/7d0efeaa9ccd4731afb386284cfdc3a9/89fa878945294931b15a581a99043005.html) (search summary)
- Web Dynpro ABAP in FLP (ABAP Platform 1909+): an app "can now store its current state in JSON format" via `SET_IN_APP_STATE` (interface `IF_WD_FLP_API`); on restart "the latest stored state is transferred to the application as new URL parameter sap-iapp-state" — [SAP Help: Fiori Launchpad Navigation API: Support for SAP InnerAppState](https://help.sap.com/doc/34796706f38646f68d51a0fa0d4636e4/100/en-US/d46d430216b546d8bdd16c5c2301a222.html)
- Practitioner reports: Fiori elements custom pages may not update `sap-iapp-state` on filter change without manual `updateAppState()` — [SAP-docs/sapui5 GitHub issue #205](https://github.com/SAP-docs/sapui5/issues/205); "appstatekey missing when navigating back" issue — [SAP Community Q&A](https://community.sap.com/t5/technology-q-a/fiori-in-app-state-issue-appstatekey-missing-when-navigating-back/qaq-p/12801222); a 403 CSRF error when saving app state via the INTEROP service — [SAP Community Q&A](https://community.sap.com/t5/technology-q-a/app-state-saving-issue-crossapplicationnavigation-error-403-in-service/qaq-p/12111511)

**Microsoft Dynamics 365 / Power Apps model-driven apps (Dataverse)**
- App URL: `https://myorg.crm.dynamics.com/main.aspx?appname={UniqueName}` or `?appid={AppModuleId}`; "you can't use both at the same time" — [Microsoft Learn: Open apps, forms, views, and reports with a URL (updated 2026-04-21)](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/open-forms-views-dialogs-reports-url)
- Record form: `main.aspx?etn=account&pagetype=entityrecord&id=%7B91330924-802A-4B0D-A900-34FD9D790829%7D`; view: `main.aspx?etn=opportunity&pagetype=entitylist&viewid=%7b...%7d&viewtype=1039`; chrome control `navbar=off&cmdbar=false` — [same page](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/open-forms-views-dialogs-reports-url)
- `etn` = table logical name. "Don't use the etc (table type code) parameter that contains an integer code for the table. This integer code varies for custom tables in different organizations." `extraqs` carries encoded nested parameters (e.g. `formid%3D...`) to pass values to a form. `viewtype` 1039 = system view (`savedquery`), 4230 = personal view (`userquery`) — [same page](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/open-forms-views-dialogs-reports-url)
- Stability: "The GUID that represents system views for system tables is the same for each installation. The GUID for custom tables and custom views is unique for each installation." Views that use user context (e.g. My Accounts) cannot be copied as URLs — [same page](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/open-forms-views-dialogs-reports-url)
- Security: "URL addressable apps, forms, views, and reports can't bypass security. Only licensed users, based on their security roles, can access the data and the records they see." — [same page](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/open-forms-views-dialogs-reports-url)
- If the user changes the view after opening via URL, the app remembers the user's most recent selection (per-user state stored server-side, separate from URL) — [same page](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/open-forms-views-dialogs-reports-url)

**Microsoft Dynamics 365 Finance & Operations**
- Deep-link form `https://<env>.cloud.dynamics.com/?cmp=USMF&mi=CustTable&CustAccount=001234`: `cmp` = legal entity/company code, `mi` = menu item (AOT name, e.g. `CustTable` = Customer details), extra params filter the record — [Confiz blog (Microsoft partner)](https://www.confiz.com/blog/what-are-deep-links-and-how-to-generate-them-in-dynamics-365-finance-operations/); sample `cmp=usmf&mi=defaultdashboard` — [Cloud Elements docs](https://docs.cloud-elements.com/home/dynamics365fo-authenticate) (both non-Microsoft; no Microsoft Learn page was retrieved in this pass)
- F&O ships a `UrlGenerator` class for building shareable deep links (used in reports, e-mails, external apps); obtaining the host via `UrlUtility::getUrl()` fails in batch because `SessionContext` is null, so batch code must read the host from environment config — [Docentric AX blog](https://ax.docentric.com/?p=11245) (search summary)

**Oracle Fusion / NetSuite**
- Oracle has an official "Create Deep Links" topic for Fusion Procurement — [Oracle docs (24C)](https://docs.oracle.com/en/cloud/saas/procurement/24c/fapaa/create-deep-links.html) — but the fetch redirected to a landing page, so the exact `deeplink?objType=…&objKey=…&action=…` format could NOT be verified in this pass. NetSuite was not researched.

### Inferences
- Common anatomy across vendors: `<host>/<tenant+env>/<shell entry>` + `<stable page id>` + `<record key>` + `<optional context>`. The page id is always a configuration-level identifier (menu item, semantic object/action, LogicalId+program) rather than a file path, which decouples links from the implementation and lets the shell resolve them (target mapping, portable links).
- Stable/bookmarkable parts: tenant/env, page id, record GUID/business key, inline query context (Infor `favoriteContext`, D365 `extraqs`/filters). Session-/time-bound parts: SAP `sap-iapp-state`/`sap-xapp-state` keys (transient by default; persistent ones still expire under cleanup), D365 CE "last selected view" (per-user server state).
- Why the patterns exist: multi-tenancy (tenant segment / `cmp`), shell + embedded apps (LogicalId, FLP hash routing, `main.aspx` single entry), deep links from email/reports/dashboards (drillback, `UrlGenerator`), cross-app navigation without hard coupling (semantic object indirection, portable links).
- D365's warning against `etc` (instance-specific integer) is directly analogous to exposing auto-increment IDs: links should use identifiers that are stable across environments (UUID/business key/hashid), not install-specific integers.
- The `sap-xapp-state` (cross-app, source app creates state for the target) vs `sap-iapp-state` (inner-app, app persists its own UI state) distinction is consistent with the community sources above, but no official SAP page retrieved in this pass spelled out `sap-xapp-state` explicitly; treat that naming split as well-known but not re-verified here.

### Gaps
- Exact Infor OS Portal v2 page-UUID URL (`/v2/<TENANT>_PRD/<UUID>?favoriteContext=<JSON>&LogicalId=…`) and whether `favoriteContext` carries percent-encoded JSON in the new portal: not confirmed by any Infor document found; only `favoriteContext=CRS610` (program id) is documented.
- SAP: key length/format of app-state keys, whether `sap-xapp-state-data` (inline JSON variant) is supported in current releases, and default `APPSTATE_TRANSIENT` value per release — official pages not reachable (403/404).
- Microsoft Learn official reference for F&O `cmp`/`mi` and `UrlGenerator` not retrieved; partner blogs only.
- Oracle Fusion deep-link parameter format not verified; NetSuite not covered.

## Q2. Translating the patterns into self-hosted Laravel 12 routing

### Takeaway
Laravel 12 provides every building block natively: a route-group prefix with a `{tenant}` (or literal env) segment filled by `URL::defaults()` in a middleware prioritised before `SubstituteBindings`; named routes as the internal page registry target; implicit model binding with custom route keys (already hashids in this repo) for record ids; and either inline query context or a short server-side state key (DB/cache, SAP-style) for long filter state. Signed / temporary signed URLs cover public or share links. No third-party service is needed.

### Cited Findings
- `URL::defaults()` sets request-wide defaults for URL parameters (doc example: `{locale}`), typically from a route middleware; "Setting URL default values can interfere with Laravel's handling of implicit model bindings", so the middleware must be prioritised before `SubstituteBindings` via `$middleware->prependToPriorityList(before: SubstituteBindings::class, prepend: ...)` in `bootstrap/app.php` — [Laravel 12.x docs: URL Generation – Default Values](https://laravel.com/docs/12.x/urls)
- Named routes decouple generated URLs from route paths: "if the route's URL changes, no changes need to be made to your calls to the route function"; extra array elements become query-string params; Eloquent models passed to `route()` contribute their route key — [Laravel 12.x docs: URLs for Named Routes](https://laravel.com/docs/12.x/urls)
- `url()->query('/posts', ['columns' => ['title','body']])` encodes arrays as `columns%5B0%5D=title&...` — [Laravel 12.x docs](https://laravel.com/docs/12.x/urls)
- Signed URLs: `URL::signedRoute()`, `URL::temporarySignedRoute(name, expiry, params)`, `$request->hasValidSignature()`, `hasValidSignatureWhileIgnoring(['page','order'])` ("ignoring parameters allows anyone to modify those parameters"), `signed` middleware returns 403 (`signed:relative` when domain excluded); `InvalidSignatureException` can render a custom "link expired" view — [Laravel 12.x docs: Signed URLs](https://laravel.com/docs/12.x/urls)
- Fluent `Illuminate\Support\Uri` (`Uri::route`, `Uri::signedRoute`, `withQuery`, `$request->uri()`) for building/manipulating URLs — [Laravel 12.x docs: Fluent URI Objects](https://laravel.com/docs/12.x/urls)
- Laravel docs site now flags 12.x as "an old version" and points to 13.x (as of 2026-10) — [Laravel 12.x docs banner](https://laravel.com/docs/12.x/urls)
- This repo already has a hashid decoding layer: `DecodeHashids` with `HASHED_PARAM_KEYS` and `PLAIN_ROUTE_PREFIXES` constants (inspected: `app/Http/Middleware/DecodeHashids.php` lines 29, 68), and AGENTS.md requires raw integers on hashed params to 404 (guarded by `tests/Feature/HashidUrlSecurityTest.php`). (Repo inspection, not a web source.)

### Inferences (proposed Laravel patterns; not implemented or tested)
1. **Tenant/environment segment.** `Route::prefix('v2/{portal}')->where(['portal' => 'ADASI_(PRD|QAS|DEV)'])->middleware(SetPortalUrlDefaults::class)->group(...)`; the middleware calls `URL::defaults(['portal' => config('portal.instance')])` (e.g. `ADASI_PRD` from env) and must be prepended before `SubstituteBindings` per the docs. For a single-tenant self-hosted app a literal prefix (`Route::prefix('v2/'.config('portal.instance'))`) is simpler and avoids the binding-priority issue; the segment is then cosmetic/environment-identifying, mirroring Infor `CONCIERGE_PRD`.
2. **Page registry with stable IDs.** A PHP config/class (e.g. `config/portal_pages.php`) mapping a stable UUIDv4/v5 or short code per menu item (`'7f3c…' => 'purchasing.requisitions.index'`) plus role/scope metadata. One catch-all route `GET v2/{portal}/{pageId}` resolves the id, authorises (role/scope), and either internally dispatches or 302-redirects to the named route. Keep the UUID immutable even if the route name changes (analogous to SAP target mapping / Infor portable links / D365 `appid`). Generating UUIDv5 from the route name gives determinism but ties it to the name — store literal UUIDs instead.
3. **Record key.** Keep using route model binding with hashids (existing `HasHashids`), never raw auto-increment IDs (same reason as D365's "don't use `etc`").
4. **Context param, two modes.** (a) Inline: `?ctx=` with base64url/percent-encoded JSON of whitelisted filter keys, validated via FormRequest; bookmarkable, but visible and length-bounded. Optionally sign it (signed route or HMAC) to prevent tampering if it influences anything beyond UI filters. (b) Server-side state key (SAP-style): persist `{key (random 32+ chars or ULID), user_id, page_id, payload JSON, created_at, last_accessed_at, read_count}` in a DB table, put `?state=<key>` in the URL; restore by key with ownership/permission check; prune with a scheduled command (SAP default analogue: delete if not accessed for N days). Make states immutable (new key per change) as SAP does, so back/forward history stays consistent.
5. **Compatibility layer.** Keep existing named routes working; add the new `/v2/...` URLs as aliases or 301/302 redirects from old paths (or vice-versa) so bookmarks, notifications (`NotificationUrlResolver`), emails, and DataTables endpoints keep functioning. Route ordering: static before dynamic catch-all.
6. **Link helper.** A single `page_url($pageId, $record = null, array $context = [])` / Blade directive wrapping `route()` so views never hand-build URLs; this is the analogue of D365 `UrlGenerator` / SAP `hrefForExternal`. Must work from queue/console (no request) by reading the instance from config — cf. the D365 batch `SessionContext` pitfall.
7. **Hashid middleware interplay.** Any new route parameter name (`pageId`, `state`) must be explicitly excluded from or added to `DecodeHashids` handling; otherwise hashed-param rules could 404 or mis-decode. Page UUIDs are not hashids.

### Gaps
- No vendor or Laravel source benchmarked internal dispatch vs redirect for a catch-all page route; trade-off (extra round-trip vs duplicate controller entry) is inference only.
- Whether `URL::defaults` interacts with route caching or `DecodeHashids` in this repo was not tested.

## Q3. Pitfalls: URL length, expiring state, cross-permission sharing, back button, analytics/log noise

### Takeaway
Inline-context URLs hit hard server limits around 8 KB (nginx and Apache defaults) and the HTTP spec only guarantees 8000 octets; key-referenced state avoids length issues but makes bookmarks expire (SAP documents this explicitly) and requires per-request authorisation on restore. Vendors uniformly state that links never bypass security, so shared links must be re-authorised for the viewer.

### Cited Findings
- HTTP: "It is RECOMMENDED that all senders and recipients support, at a minimum, URIs with lengths of 8000 octets in protocol elements" — [RFC 9110 §4.1](https://www.rfc-editor.org/rfc/rfc9110.html)
- nginx: `client_header_buffer_size 1k` default; `large_client_header_buffers 4 8k` default; "A request line cannot exceed the size of one buffer, or the 414 (Request-URI Too Large) error is returned to the client"; an over-long header field returns 400 — [nginx ngx_http_core_module](https://nginx.org/en/docs/http/ngx_http_core_module.html)
- Apache httpd 2.4: `LimitRequestLine` default 8190 bytes; it "places a restriction on the length of a request-URI"; "A server needs this value to be large enough to hold any of its resource names, including any information that might be passed in the query part of a GET request"; "Under normal conditions, the value should not be changed from the default"; with name-based virtual hosting the value comes from the default (first-listed) vhost — [Apache core docs: LimitRequestLine](https://httpd.apache.org/docs/2.4/mod/core.html#limitrequestline)
- SAP: bookmarked/shared app-state links only work while the state still exists on the front-end server; cleanup deletes states not accessed for (default) 365 days — [SAP Help: Cleanup of Expired Application State](https://help.sap.com/doc/saphelp_nw75/7.5.5/en-US/ff/b437e68f464478bbd723ca144a22d7/content.htm?no_cache=true)
- SAP: transient (default) app state is browser/session-local and cannot be reproduced on other browsers/devices; bookmarks may open the base state; state may be lost after launchpad timeout — [SAP Community: app state for sharing](https://community.sap.com/t5/technology-blog-posts-by-sap/configuration-of-fiori-app-state-for-sharing/ba-p/14240470); [SAP KBA 3260742](https://userapps.support.sap.com/sap/support/knowledge/en/3260742) (search summaries)
- SAP: app-state keys change on every state change (immutable states); practitioners report missing state keys on back navigation and URLs not updating on filter change — [SAP blog 2017](https://blogs.sap.com/2017/06/19/restoring-fiori-application-state/); [SAP Community Q&A](https://community.sap.com/t5/technology-q-a/fiori-in-app-state-issue-appstatekey-missing-when-navigating-back/qaq-p/12801222); [SAP-docs issue #205](https://github.com/SAP-docs/sapui5/issues/205)
- Microsoft: URL-addressable forms/views "can't bypass security"; user-context views (My Accounts) can't be shared as URLs; custom view GUIDs differ per installation — [Microsoft Learn](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/open-forms-views-dialogs-reports-url)
- Infor: if the portal shell is not present, a drillback is ignored and a fallback action runs (links depend on the shell context) — [Infor d/EPM docs](https://docs.infor.com/depm/2024.x/en-us/depmolh_cloud/application_studio_cloud/mrh1678908470941.html) (search summary)
- Laravel: `hasValidSignatureWhileIgnoring` lets anyone change ignored params; expired temporary signed URLs return 403 unless a custom `InvalidSignatureException` renderer is defined — [Laravel 12.x docs](https://laravel.com/docs/12.x/urls)

### Inferences
- Practical cap: keep generated URLs well under ~2 KB to stay safe with proxies, logs, email clients and copy/paste, even though server defaults allow ~8 KB; above a threshold, switch from inline `ctx` to a server-side state key automatically. (The ~2 KB figure is a common practitioner rule of thumb; no authoritative source was retrieved for it.)
- Shared links across users with different permissions: the receiving user's role/scope must be checked on every resolve (page id → route authorisation, record → policy, state key → owner or re-validated payload). For this repo, supplier isolation (`supplier_id = auth()->id()`) and `supplier.scope:*` must apply even when a Purchasing user shares a page link with a supplier. A state key owned by user A should either be private to A or contain only non-sensitive filter values that are re-applied under user B's own query scope.
- Expiry UX: an expired/unknown state key should degrade to the page's base state with a toast ("saved view expired"), not a 404 — mirroring SAP behaviour but surfaced explicitly.
- Back button: immutable state keys + `history.pushState/replaceState` per meaningful change keep history coherent; mutating a state row in place would make Back show the new state. Server-tabs/AJAX filter changes in this repo (`AdasiServerTabs`) would need to update the URL accordingly.
- Analytics/log noise: random state keys and JSON contexts explode distinct URL counts in access logs and analytics; logging the page id (route name) separately and stripping/normalising `state`/`ctx` query params avoids this. Long percent-encoded JSON also bloats access logs and may leak filter values (e.g. supplier names) into logs and Referer headers; a `Referrer-Policy` header and server-side keys mitigate this.
- Search engines are not a concern for an authenticated portal, but `noindex` and `no-store` on state-bearing pages remain sensible.
