# ADASI Portal Supplier: current logout path and options for an Infor-like "signing out..." experience

Scope: read-only inspection of the master worktree (HEAD 1c4ab2c) at `/tmp/claude-0/-home-user-supplierportal/ea3de87b-cf7c-506d-839d-81a9d28a95c4/scratchpad/master-tree` (called `<master>` below). All paths are relative to `<master>`. Line numbers are file-local. Nothing was executed (no tests, no migrations). `vendor/` is not installed in the worktree, so Laravel framework internals (SessionGuard) were NOT inspected; statements about them are labelled as framework behaviour from general knowledge.

## 1. What does the current logout path do (server side)?

### Takeaway
Logout is a single root-level `POST /logout` (route name `logout`, `auth` middleware only, CSRF-protected by the web group) handled by `AuthenticatedSessionController::destroy`, which does guard logout, session invalidate, CSRF regenerate, optionally stamps an auth-splash marker, and 302s to `/login`. Only the current browser session is ended; nothing is revoked elsewhere, no client state is cleared, and no cross-tab signal is sent.

### Cited Findings
- Route: `Route::post('logout', [AuthenticatedSessionController::class, 'destroy'])->name('logout');` inside `Route::middleware('auth')` group, with no `no-store`, `auth.session` or throttle middleware on it. POST only; there is no GET logout route. `routes/web.php:775` (group), `:786-787` (route).
- Controller: `Auth::guard('web')->logout()` (`app/Http/Controllers/Auth/AuthenticatedSessionController.php:72`), `$request->session()->invalidate()` (`:74`), `regenerateToken()` (`:76`), then if `config('ui.auth_splash.enabled', false)` puts `ui.auth_splash` = {id uuid, reason `post-logout`, issued_at, target null} (`:78-85`), and `redirect()->route('login')` (`:87`). The redirect is always to `/login`, regardless of JSON or HTML requests (test `tests/Feature/Auth/AuthSplashTest.php:203-208` asserts a JSON POST also gets the redirect).
- Web middleware stack applied to every web route (so also logout): `ApplyUserLocale, ShareAuthSplashState, DecodeHashids, EnforceAuthSessionSecurity, EnsureSsoSession, EnforcePasswordChange, AddSecurityHeaders, EnforceSupplierDomain, LimitOperationalRequests` (`bootstrap/app.php:88-98`); `authenticateSessions()` at `:86`.
- `EnsureSsoSession` explicitly exempts `logout` (`app/Http/Middleware/EnsureSsoSession.php:19-24`), and `EnforcePasswordChange` exempts it too (`app/Http/Middleware/EnforcePasswordChange.php:13`), so a user with an unverified SSO session or forced password change can still log out.
- Navbar logout is a plain HTML form (`method="POST"`, `@csrf`), no JS, no `data-async-submit` (`resources/views/partials/navbar.blade.php:162-167`; asserted by `tests/Feature/UserAccountNavigationTest.php:40-43`). `resources/js/unsaved-changes.js:57` excludes forms whose action ends in `/logout` from unsaved-change warnings.
- Audit: Laravel's `Logout` event is listened by `LogAuthenticationEvent::handleLogout` (`app/Providers/AuthSecurityServiceProvider.php:41`) which writes audit event `logout` with guard metadata (`app/Listeners/LogAuthenticationEvent.php:48-56`), unless the request attribute `auth_security.suppress_logout_audit` is set (`:50`). That suppress flag is set by forced terminations (`EnforceAuthSessionSecurity::terminateSession` line 74, `TwoFactorService.php:46`), which instead emit their own `AuthSecurityEvent` (e.g. `session_revoked`, `session_timeout`, `account_deactivated`, `remember_mfa_required`; `EnforceAuthSessionSecurity.php:28,33,53,64`).
- `AuthAuditLog` rows are pruned at 180 days (`config/auth_security.php:123`); `logout` rows are not specially retained.
- PortalPath/Infor-style URLs: `logout` is in `ROOT_SEGMENTS` (`app/Support/PortalPath.php:11`), the AGENTS.md rule states logout stays at root when the prefix is enabled (AGENTS.md line 374), and the logout route is registered outside the `Route::prefix(PortalPath::prefix())` group (the prefix group starts at `routes/web.php:789` and only wraps profile security routes). Tests: `tests/Feature/PortalPathPrefixTest.php:34,120`, `tests/Unit/PortalPathTest.php:60`. So any new logout page/route should also be added to `ROOT_SEGMENTS`, otherwise the prefix-validation boot check (AGENTS.md:374) and fallback redirects would treat it as a prefixed path.
- `SsoTransactionStore::safeIntendedUrl` refuses to use `logout`, `login`, `oauth`, `sso`, `two-factor-challenge`, `confirm-password` as an intended URL (`app/Services/Auth/Sso/SsoTransactionStore.php:101-103` file-local), so a post-login redirect never lands on logout.

### Inferences
- Because the logout route sits behind `auth`, an unauthenticated POST (session already expired) never reaches `destroy`; see section 5 for what the user sees.
- Adding a new GET interstitial would need to respect the same exemptions (`EnsureSsoSession` exempt list at `EnsureSsoSession.php:19-24`, `EnforcePasswordChange.php:13`, `PortalPath::ROOT_SEGMENTS`) or a user with must_change_password / unverified SSO would be bounced.

### Gaps
- Not inspected: Laravel's `SessionGuard::logout()` internals (vendor missing). General framework behaviour (not verified here): it fires `Logout`, queues removal of the recaller (remember-me) cookie, and cycles the user's `remember_token` if one exists. Reference: Laravel authentication docs, "Logging Out" (https://laravel.com/docs/12.x/authentication#logging-out) - not fetched in this session.

## 2. Which other state exists on the server (session rows, remember token, SSO/Passport, known device, other-device logout)?

### Takeaway
Sessions are DB-backed (`sessions` table, 120 min idle, 480 min absolute). Normal logout deletes only the current session (via `invalidate()`); other sessions of the user continue. The "log out other devices" feature exists on the Security page and uses a per-user `auth_session_version` counter plus remember-token rotation. SSO (Passport) is a login-time OAuth+PKCE handshake against the same app; Passport tokens are revoked immediately at callback, so there is nothing to revoke at logout.

### Cited Findings
- Session driver default `database` (`config/session.php:21`), idle lifetime 120 min (`:35`), `expire_on_close` false (`:37`), cookie secure/same-site strict-ish in production (`:174-210`, not read in full). Absolute timeout 480 min `AUTH_ABSOLUTE_TIMEOUT` (`config/auth_security.php:108`), concurrent-session cap 3 (`:114`).
- Absolute timeout/version check lives in `EnforceAuthSessionSecurity.php:48-66`: compares `session('auth_session_version')` with `users.auth_session_version`; mismatch triggers `terminateSession(... 'session_revoked')` (`:52-53`). `terminateSession` (`:71-84`) logs out, invalidates, regenerates the token, returns 401 JSON for `expectsJson()` or redirects to `login` with status flash `auth.feedback.session_ended`.
- `SessionRevocationService::revokeOtherSessions` bumps `auth_session_version` and rotates `remember_token` (`app/Services/Auth/SessionRevocationService.php:16-28`); `invalidateRememberTokens` rotates the remember token and re-queues the current device's recaller cookie (`:37-59`).
- "Log out other devices" feature: `POST profile/logout-other-devices` requires `auth.session` + `throttle:auth.credentials` (`routes/web.php:790-792`), controller validates `current_password`, calls `Auth::logoutOtherDevices()` and `revokeOtherSessions($user, $request, false)` (`app/Http/Controllers/Auth/LogoutOtherDevicesController.php:13-20`); audit event `other_device_logout` (`LogAuthenticationEvent.php:120`). Single-session revoke: `DELETE profile/sessions` (`routes/web.php:798-800`) -> `RevokeSessionController` which deletes the selected `sessions` row via `SessionInventoryService::revoke` (`SessionInventoryService.php:35-41`) then rotates remember tokens and audits `session_revoked` (`RevokeSessionController.php:42-43`). UI: `resources/views/profile/security.blade.php:44-49` and `profile/partials/logout-other-devices-form.blade.php`. Password update also calls `Auth::logoutOtherDevices` (`app/Http/Controllers/Auth/PasswordController.php:35`).
- Concurrent-session eviction deletes oldest session rows beyond the limit (`SessionInventoryService.php:43-73`). Evicted/revoked tabs only discover this on their next request (see section 4).
- Known-device cookie `adasi_known_device` (httpOnly, lax, lifetime 400 days, `config/auth_security.php:117-120`) is queued only at login (`app/Services/Auth/KnownDeviceService.php:15-20,64-77`). Nothing in logout touches it, and that is intentional: it identifies the browser for "new device" alerts, so clearing it on logout would cause an alert on every login. Test confirming reuse after logout: `tests/Feature/Auth/KnownDeviceSecurityTest.php:80-95`.
- SSO is opt-in (`SSO_LOGIN_ENABLED=false` default per AGENTS.md:824). `GET /login` is `SsoEntryController@start` (`routes/web.php:744-745`). The callback exchanges the code in-process, verifies JWT sub/aud, then in the same DB transaction revokes the refresh and access tokens (`app/Http/Controllers/Auth/SsoCallbackController.php:84-87`) and only then writes the session proof `sso.verified_at` / `sso.client_id` (`:105-108`). AGENTS.md:825 states "no operational token or API guard" exists. The proof lives only in the Laravel session, so the existing session invalidation at logout destroys it. `EnsureSsoSession` forgets/re-requests proof when absent (`EnsureSsoSession.php:36-53`).
- Passport purge is scheduled 02:40 when SSO enabled (AGENTS.md:826).

### Inferences
- With SSO enabled, there is no distinct "SSO session" at an IdP to terminate: the IdP and the client are the same Laravel app and the same session. Logout destroying the session is already a full logout of both.
- Remember-me: if framework default `SessionGuard::logout()` behaviour holds (unverified here), the recaller cookie on the current browser is cleared and the token cycled. Caveat: the remember token is shared across all devices of one user (the code comments say so, `SessionRevocationService.php:30-36`), so a normal logout on device A that cycles the token would silently invalidate recaller cookies on device B (they would just need to log in again if their session row is gone; sessions in DB remain valid). Not verified by test; worth a quick test before relying on it.

### Gaps
- Did not verify whether `SessionGuard::logout()` actually cycles the remember token in the installed Laravel 12 version (vendor absent).
- `sessions` table rows: `invalidate()` deletes the current row through the DB session handler; not traced in vendor.

## 3. What client-side state exists that a logout should clear?

### Takeaway
There is a moderate amount of per-browser state surviving logout: localStorage (sidebar prefs per account, pending export job records NOT scoped to the user, supplier-registration draft, quotation drafts, audit-guide toggle), sessionStorage (chat drafts keyed by user id, PO upload status URL, finance scroll position, import toast), an in-memory server-tabs fragment cache that disappears on navigation, and a live Pusher/Echo websocket plus 30 s badge polling that only stop on a full page navigation.

### Cited Findings
- Sidebar: `localStorage['adasi.sidebar.'+accountId]` revision/collapsed (`resources/views/layouts/app.blade.php:30,36,40,70`). Keyed per account; harmless.
- Pending exports: `localStorage['adasi:pending-export-jobs:v1']` (`public/assets/js/async-export.js:12,236,252`; also written inline in `resources/views/finance/drp/paid.blade.php:613-626` and `finance/drp/supplier.blade.php:304-317`), plus download-claim keys (`async-export.js:347-361`). The key is NOT user-scoped; records are export job IDs (hashids). Cross-user leak on a shared PC is limited to IDs, but still stale state after logout. (Inferred: the server enforces ownership on status/download, per AGENTS.md "ownership saat polling/download".)
- Supplier registration draft: `localStorage['adasi_supplier_reg_draft']` and sessionStorage keys (`resources/views/auth/supplier-register.blade.php:1776,1816-1847,1915-2023`); passwords are not stored (`:2001`). This is a public (pre-login) page and should NOT be cleared by logout (a draft owned by a not-yet-user).
- Quotation drafts: `localStorage['quotation_draft_'+prId]` (`resources/views/supplier/quotations/create.blade.php:2794,2807,2821`). Not user-scoped (PR id only): on a shared browser, user B could see user A's quotation draft for the same PR. Clearing on logout would be a real privacy/data-hygiene benefit; trade-off: a supplier that logs out mid-draft loses the draft (the user's own expectation under "Signing out" is arguably that draft persists; this is a product decision).
- Chat drafts: `sessionStorage['adasi_chat_draft_'+myId+'_'+conversationId]` (`resources/views/partials/chat-drawer.blade.php:142-171`); sessionStorage is per-tab and cleared when the tab closes.
- Others: `sessionStorage` PO upload status URL (`resources/js/po-document-upload.js:16,79`), local import toast (`resources/js/local-procurement-import.js:34-49`), finance invoice verify scroll (`finance/invoices/show.blade.php:601,697,747`), `localStorage['supplierAuditScoreGuide']` UI toggle (`local-supplier/supplier-audits/edit.blade.php:147-148`).
- No IndexedDB, BroadcastChannel, service worker or Cache API usage found by grep across `resources/js`, `public/assets/js`, `resources/views`.
- Server-tabs cache: in-memory `Map` (`resources/js/server-tabs.js:26-64`, TTL 5 min) - lives only until the document unloads; logout is a full navigation so it is already discarded. The user-preference payload is injected into the page per request (`layouts/app.blade.php:23`) and not persisted client side other than the sidebar key.
- Realtime and polling: Echo is created only when Pusher is configured (`layouts/app.blade.php:1074-1096`), private channel `App.Models.User.{id}` authorised via `/broadcasting/auth` with CSRF header (`:1090-1101`; `routes/channels.php:5-7` returns false for inactive/other users). Badge polling `setInterval(updateBadges, 30000)` skipped when the tab is hidden (`:415-418, 509`), calls `notifications.unread-count` and (for Purchasing / Import suppliers) `conversations.unread-count`. Chat drawer polls messages every 8 s while a conversation is open (`chat-drawer.blade.php:611,635`). Export status polling in `async-export.js` (401 handled at `:765,943`).
- After logout on a single tab, the navigation to `/login` unloads the document, so that tab's Echo socket/pollers die with it. Echo has no explicit `disconnect()` call and no `pagehide` handler (grep of `layouts/app.blade.php` shows none), but page unload closes the websocket in practice.

### Inferences
- Real client-side cleanup candidates: the two non-user-scoped keys (`adasi:pending-export-jobs:v1`, `quotation_draft_*`) and sessionStorage drafts. Everything else is harmless/UI-only or must be kept (registration draft, known-device cookie).
- A deterministic "clean state" step could run on the interstitial page (JS: remove specific keys by prefix list) or be achieved via `Clear-Site-Data: "storage"` (see section 6), but the latter is origin-wide and would also delete the registration draft and sidebar preferences.

### Gaps
- Did not verify whether the pending-export/quotation keys are consumed after logout by a different account in a real browser.

## 4. What happens to other tabs, other devices, expired sessions, the back button, and GET logout today?

### Takeaway
Other tabs in the same browser are NOT notified: they keep running until their next request, which is either the 30 s badge poll (silently ignores a 401/redirect) or a user click (redirected to login). Back button after logout does not reveal protected content because every response is `no-store, private`, but the HTML a tab already holds stays visible until it navigates. GET /logout is not routable (405 -> mapped to 404/405 by fallback). Expired-session POST gets a 419 page with a "sign in again" button.

### Cited Findings
- Cache headers: `AddSecurityHeaders` sets `Cache-Control: no-store, private` and `Pragma: no-cache` on every non-public response (`app/Http/Middleware/AddSecurityHeaders.php:22-25`); `NoStoreResponse` (`app/Http/Middleware/NoStoreResponse.php:13-14`) does the same on routes that declare `no-store` (login, 2FA etc). So the logout redirect response and `/login` are not cached.
- Other tab polling after the session is gone: `updateBadges` fetches with `Accept: application/json` and does `r.ok ? r.json() : null` then `.catch(() => {})` (`layouts/app.blade.php:430-438,466-470`), i.e. a 401 is swallowed silently; no redirect to login and no toast. The server answers 401 JSON for these routes (`bootstrap/app.php:141-146` and `EnsureSsoSession.php:43-47`). Export polling handles 401 with a "session expired" message (`async-export.js:765,943`). Only `supplier-audit-form.js:176` and `po-document-upload.js:37` treat 401/419 specially in page scripts.
- So after logout in tab A, tab B shows stale authenticated UI until the user clicks; the next full navigation then 302s to `login` (via `redirectUsersTo`/authenticate middleware); a form POST from tab B hits CSRF mismatch because the session was invalidated -> 419 page (`resources/views/errors/419.blade.php:1-40`, buttons Reload and `route('login')` "sign in again").
- Echo/Pusher in tab B: the private channel subscription was authorised once; no re-auth until reconnect. Because `/broadcasting/auth` needs the session, a reconnect after logout fails, but already-subscribed sockets keep receiving broadcast notifications for that user until the page is closed (Pusher authorises at subscribe time; general Pusher behaviour, not verified in this code base). Notification payloads are shown as toasts (`layouts/app.blade.php:1101-1127`).
- Other devices: unaffected by normal logout. Only the other-devices/revoke features or password change revoke them (section 2).
- Back button: no history manipulation exists at logout; the redirect response replaces nothing in history. Browsers may show the previous page from bfcache; whether Chrome/Firefox/Safari bfcache `no-store` pages differs by browser (MDN/web.dev bfcache docs were not fetched; unverified). `Clear-Site-Data: "cache"` is documented to clear bfcache entries in supporting browsers ([MDN Clear-Site-Data](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Clear-Site-Data)).
- GET logout: only a POST route exists; fallback controller maps unknown methods to 404/405 (`bootstrap/app.php:128-139`). CSRF-logout risk therefore does not exist today; keep POST + CSRF for any new design.
- Expired session: a user whose session expired and who clicks Logout sends a POST with a stale CSRF token -> 419 page (not a redirect to login), a small UX wart unrelated to signing-out animation. If the session cookie is gone entirely, CSRF also fails (419) before `auth`.
- Remember-me with 2FA: a recaller-authenticated user with 2FA is forced through the 2FA challenge (`EnforceAuthSessionSecurity.php:31-46`).

### Inferences
- The biggest real gap vs an Infor-like logout is the other-tab behaviour: stale tabs of the same browser keep looking logged in (and may receive Pusher notifications) until used.
- bfcache: since there is no `pageshow` handler that re-validates the session, if a browser restores a stale page from bfcache after logout, protected content could flash; the next action would redirect. Low risk, not tested.

### Gaps
- Real browser behaviour of back button / bfcache with `no-store` not tested (no browser run permitted).
- Pusher private-channel behaviour after server-side session end not verified.

## 5. What would an Infor-like "signing out..." experience require, and which options are worth it?

### Takeaway
Only options 3 (cross-tab broadcast) and, to a lesser degree, 2 (interstitial that clears specific client keys and closes Echo) give real benefit; option 4 (Clear-Site-Data) is a blunt tool that would delete things the portal wants to keep. Option 5 already exists in the product. Option 6 does not apply today.

### Cited Findings (facts used for the options)
- `Clear-Site-Data` directives: `"cache"`, `"cookies"`, `"storage"` (localStorage, sessionStorage, IndexedDB, service workers), `"executionContexts"` (reloads all browsing contexts for the origin), `"*"`; secure context (HTTPS) only; cookies scope is the whole registered domain including subdomains; storage/cache is origin-scoped; Baseline widely available since September 2023 but MDN notes varying support per part - [MDN Clear-Site-Data](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Clear-Site-Data).
- `BroadcastChannel` lets documents (windows, tabs, frames, iframes) of the same origin communicate; messages are delivered to other `BroadcastChannel` objects of the same name, not the sender; Baseline widely available since March 2022; also in workers - [MDN BroadcastChannel](https://developer.mozilla.org/en-US/docs/Web/API/BroadcastChannel). (MDN page gives no detail on storage-partition limits, private windows or bfcache.)
- Existing CSP (`AddSecurityHeaders.php:55-67`): `default-src 'self'`, `script-src 'self' 'unsafe-inline' 'unsafe-eval' ...`, `connect-src 'self' ws: wss: https://*.pusher.com wss://*.pusher.com`, `form-action 'self'`. Inline script (needed for an inline cross-tab listener) and `BroadcastChannel`/`localStorage` need no new CSP entries. A `Clear-Site-Data` header is a response header and is not governed by CSP.
- The auth splash feature (`config/ui.php:3-11`, `AUTH_SPLASH_ENABLED` default false; `ShareAuthSplashState` markers `post-login`/`post-logout`, 30 s TTL, document-navigation only, `ShareAuthSplashState.php:166,175,144,186`) already shows a full-screen splash on the login page after logout (min visible 2000 ms, hard timeout 10 s). It is a post-logout cosmetic overlay rendered on `/login`, wired through `partials/auth-splash-bootstrap.blade.php` and `components/ui/auth-splash.blade.php`; tests in `tests/Feature/Auth/AuthSplashTest.php:190-208` and `tests/Support/auth-splash-browser-check.mjs`. It does not clear anything.

### Options

1. Keep as is. Effort 0. Risk 0. Deficiency: stale tabs, non-user-scoped localStorage keys, no explicit end state.
2. Interstitial "Signing out..." page. Effort: small-medium (new GET page or reuse the existing splash; or make the navbar form `fetch` POST then `location.replace('/login')`). The page would: remove a fixed list of keys (`adasi:pending-export-jobs:v1`, `quotation_draft_*`, `adasi_chat_draft_*`, sessionStorage), call `window.Echo?.disconnect()`, then navigate. Real benefit is limited: the server logout already completed; client cleanup could equally be done on the `/login` page load for guests. Mostly cosmetic, with a small real part (explicit Echo disconnect and key cleanup). Risks: a GET interstitial that triggers logout would be CSRF-able (keep POST); must be root-level and exempt from `EnsureSsoSession` / `EnforcePasswordChange` / `PortalPath::ROOT_SEGMENTS`; the existing splash flow (`post-logout` marker issued only when `$request->routeIs('logout')` POST, `ShareAuthSplashState.php:144`) assumes the redirect target is `/login`; with `fetch` logout, `ui.auth_splash` handling and the 302 are fine (the session cookie updates via Set-Cookie), but the JSON-logout test (`AuthSplashTest.php:203-208`) shows the controller always redirects, so fetch must follow redirects or the controller must return JSON for `expectsJson()`.
3. Cross-tab logout broadcast. Effort: small (about 20-40 lines JS in `layouts/app.blade.php` or a new Vite module): on logout submit, `new BroadcastChannel('adasi-auth').postMessage({type:'logout'})` (fallback: `localStorage.setItem('adasi:logout', Date.now())` + `storage` event for old browsers); other tabs listen and `location.replace('/login')`. Plus optionally make `updateBadges` treat 401 as "session ended" and redirect to login (the server already returns 401 for these polling routes, `bootstrap/app.php:141-146`; currently swallowed at `layouts/app.blade.php:430-438`). The 401-on-poll change also kicks tabs after a revocation from another device/admin deactivation (`EnforceAuthSessionSecurity.php:27-29,52-53`), which BroadcastChannel cannot. Real UX and security benefit, small risk (same-origin only, no payload secrets). Needs guard against kicking a tab on a transient 401 during session regenerate, and against redirect loops on public pages (only emit/listen when `@auth`). Does not help other devices.
4. `Clear-Site-Data` on the logout response. Effort: tiny (one header on the redirect response in `destroy`). Behaviour per MDN: `"storage"` wipes all localStorage/sessionStorage/IndexedDB for the origin (including sidebar prefs and any public registration draft `adasi_supplier_reg_draft`, `auth/supplier-register.blade.php:1776-2023`); `"cookies"` clears every cookie for the registered domain and subdomains, including `adasi_known_device` (would trigger new-device alerts at every login, `KnownDeviceService.php:15-77`) and any sibling apps on the same registered domain (risk to other subdomains, e.g. a future Infor-style host); `"cache"` may drop bfcache entries (a mild benefit for back-button hygiene); `"executionContexts"` reloads all other tabs of the origin, which incidentally gives cross-tab logout, but support/behaviour varies and it is documented only as reloading contexts (not verified across browsers). Must be sent over HTTPS (secure context); the header must be on a response to a request in the origin (works on a 302). Recommended only as `Clear-Site-Data: "cache"` (and maybe `"executionContexts"` after testing); not `"cookies"` or `"*"`. Moderate risk, hard to test without real browsers; Safari support was not confirmed from the MDN page text I could read.
5. "Sign out from all devices". Effort: very small, already exists as `profile.logout-other-devices` (`routes/web.php:790-792`) requiring the current password. A variant for logout itself would be: add an optional checkbox on the logout form that calls `SessionRevocationService::revokeOtherSessions($user, $request, true)` before `destroy`. Real benefit (security), low risk; needs an audit event and a decision on whether password re-entry is required (existing flow requires it; a checkbox without password is a weaker policy). `revokeOtherSessions` increments `auth_session_version` which invalidates every other session (including the current one unless re-put in the session, `SessionRevocationService.php:23-25`), which is fine immediately before logout.
6. True SLO to other apps. Not applicable now: the portal is both IdP (Passport) and the only client; the "SSO session" is the Laravel session; Passport tokens are revoked at callback (`SsoCallbackController.php:84-87`) so nothing remains to revoke; AGENTS.md:825 states no operational token/guard exists. If other apps were ever registered as Passport clients, a back-channel logout would be: store per-client logout URIs; at `destroy` (and in `terminateSession`), enumerate the user's active client sessions (a new table mapping `session_id` + `client_id` + `sub`), POST a signed logout token (JWT with `sub`, `sid`, `events` claim per OIDC Back-Channel Logout) to each client's back-channel URI from a queued job, and revoke that user's Passport tokens/refresh tokens. That would be a new feature with its own table and tests, plus front-channel iframes are blocked by the current CSP (`frame-src https://challenges.cloudflare.com`, `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `AddSecurityHeaders.php:38,57-66`). OIDC Back-Channel Logout spec was not fetched in this session; the description is a design sketch (inference), not verified against the spec text.

### Inferences (recommendation)
- Real benefit: option 3 (cross-tab broadcast + 401-on-poll redirect) and option 5 (optional sign-out-all-devices). Cosmetic: option 2 interstitial, and the already-existing post-logout splash. Option 4 is mostly harmful or redundant except `"cache"`.
- Minimal recommended set: (a) option 3 including making `updateBadges` treat 401 as session end and redirecting to `/login`; (b) a small client cleanup of the two non-user-scoped keys (`adasi:pending-export-jobs:v1`, `quotation_draft_*`) and chat drafts, executed in the same logout click handler or on the guest `/login` page (no new server route, no CSP change); (c) optionally enable the existing splash (`AUTH_SPLASH_ENABLED=true`) for the "signing out" feel instead of building a new interstitial; (d) optionally the sign-out-all-devices checkbox. Skip option 4 beyond maybe `"cache"`, and skip option 6.
- A deterministic interstitial is only worth building if the product wants an explicit "Signing out..." state with Echo disconnect; since the redirect already unloads the page (and the websocket), the benefit is perceptual.

### Gaps
