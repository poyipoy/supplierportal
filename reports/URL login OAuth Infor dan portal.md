# URL panjang Infor menandakan arsitektur, bukan keamanan

URL login Infor yang panjang bukan fitur keamanan yang sengaja dipasang. URL itu adalah **jejak protokol OpenID Connect Authorization Code + PKCE (S256)**: portal Ming.le (`mingle-portal…`) tidak menemukan sesi Anda, lalu mengirim browser ke authorization server terpisah (`mingle-sso…`). Semua konteks yang dibutuhkan server itu (siapa client-nya, ke mana hasil login dikembalikan, nilai anti-CSRF, dan hash PKCE) dibawa sebagai query string. Pola ini memang yang direkomendasikan RFC 9700 (BCP 240, Januari 2025). Namun **panjangnya sendiri tidak menambah keamanan apa pun**: semua nilai di URL itu publik menurut desain. Perlindungannya datang dari entropi `state`, PKCE yang mengikat authorization code ke rahasia di backend, pencocokan `redirect_uri` yang eksak, dan TLS. ADASI Portal Supplier *bisa* menghasilkan URL serupa, misalnya dengan Laravel Passport di aplikasi yang sama atau authorization server self-hosted. Tetapi untuk satu monolit Blade dengan satu tabel `users`, ancaman yang dijawab parameter OAuth (pencurian authorization code, injeksi code, mix-up antar-server) sebagian besar **tidak ada**. Meniru URL panjang tanpa IdP sungguhan justru menambah risiko kebocoran lewat history, log, dan bookmark, sekaligus melatih supplier menerima URL login yang tidak bisa dibaca. Investasi yang benar-benar menaikkan keamanan adalah passkey/WebAuthn (satu-satunya kontrol yang mematahkan phishing proxy real-time), idle timeout yang lebih ketat untuk role keuangan, notifikasi email untuk event keamanan, dan cek password bocor secara offline. IdP terpisah baru layak bila muncul kebutuhan identitas bersama: SSO lintas aplikasi, login staf dengan direktori korporat, atau client mobile/API.

## Setiap parameter di URL Infor punya satu tugas protokol

Yang terjadi saat membuka `https://mingle-portal.ne1.inforcloudsuite.com/v2/V9ZL2J5PMG6EVXNW_PRD` adalah redirect 302 ke endpoint otorisasi milik tenant. Bentuk permintaan ini persis yang didefinisikan RFC 6749 §4.1.1: `response_type`, `client_id`, `redirect_uri`, `scope`, dan `state`, dikirim sebagai query parameter lewat redirect browser ([RFC 6749](https://www.rfc-editor.org/rfc/rfc6749)). RFC 7636 menambahkan `code_challenge`/`code_challenge_method` ([RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)), dan OIDC Core mewajibkan scope `openid` agar respons token berisi ID Token ([OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html)).

```
https://mingle-sso.ne1.inforcloudsuite.com/V9ZL2J5PMG6EVXNW_PRD/as/authorization.oauth2
  ?client_id=infor~g-LqhqFwRI302t7LUEwulql9ZhdyRrmgCVeX1VWUVTE_OIDC
  &response_type=code
  &redirect_uri=https://mingle-portal.ne1.inforcloudsuite.com/sso/callback
  &scope=openid
  &state=V9ZL2J5PMG6EVXNW_PRD~zki6OLJb...
  &code_challenge=r2_epEx7AXK3DjPQZnONkC8xM-XljiXqrNFXFJrcPuc
  &code_challenge_method=S256
```

| Bagian | Arti | Fungsi keamanan / catatan |
|---|---|---|
| `mingle-portal.ne1…` | Portal Ming.le = *client / relying party* | Tidak pernah melihat password; hanya menerima token untuk dirinya |
| `mingle-sso.ne1…` | Authorization server / OpenID Provider (InforSTS + Federation Hub) | Cookie SSO-nya host-only, jadi tidak terbaca oleh XSS di aplikasi lain |
| `ne1` | Sel cloud regional; ada sepupu `eu1` ([DocBits](https://docbits.com/doc/docbits-with-infor/infor-sso/)) | Arti "North America East" adalah **dugaan**, belum dikonfirmasi Infor |
| `V9ZL2J5PMG6EVXNW_PRD` | Tenant + lingkungan (`_PRD` = produksi) | Memilih konfigurasi AS per tenant: user, federasi IdP, client, kunci tanda tangan ([Infor ION API file](https://docs.infor.com/crm/9.2.x/en-us/webclient/upi1639111995644.html)) |
| `/as/authorization.oauth2` | Path endpoint otorisasi bergaya PingFederate | Lihat catatan ketidakpastian di bawah |
| `client_id=infor~…_OIDC` | Identitas client portal | **Bukan rahasia** (RFC 6749 §2.2). Arti prefiks `infor~` dan sufiks `_OIDC` hanya inferensi |
| `response_type=code` | Minta authorization code, bukan token | Token tidak pernah muncul di URL; code berumur pendek (≤10 menit disarankan) dan sekali pakai ([RFC 6749 §4.1.2](https://www.rfc-editor.org/rfc/rfc6749#section-4.1.2)). Implicit grant dilarang RFC 9700 §2.1.2 |
| `redirect_uri=…/sso/callback` | Satu-satunya tujuan pengiriman code | AS **wajib** mencocokkan string secara eksak dengan nilai terdaftar ([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)) |
| `scope=openid` | Mengubah OAuth biasa menjadi login OIDC | Menghasilkan ID Token (JWT bertanda tangan) yang mengidentifikasi user |
| `state=TENANT~acak…` | Nilai opak yang dikembalikan utuh | Anti-CSRF/login-CSRF, dan kunci lookup ke `code_verifier` serta deep link asal. Prefiks tenant kemungkinan membantu callback bersama (`/sso/callback` tanpa tenant di path) memilih token endpoint yang benar. Struktur ini **diinferensikan**, tidak didokumentasikan Infor |
| `code_challenge` (43 karakter) | `BASE64URL(SHA256(code_verifier))` | Code curian tidak bisa ditukar tanpa verifier. Hasil decode lokal: tepat 32 byte, yaitu satu digest SHA-256 |
| `code_challenge_method=S256` | Metode PKCE | "Saat ini S256 satu-satunya metode" yang tidak membuka verifier ([RFC 9700 §2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html)) |

Path `/as/authorization.oauth2` adalah endpoint otorisasi PingFederate yang terdokumentasi, berpasangan dengan `/as/token.oauth2` ([PingFederate OAuth 2.0 endpoints](https://docs.pingidentity.com/pingfederate/latest/developers_reference_guide/pf_oauth_20_endpoints.html)). Berkas kredensial ION API milik Infor sendiri juga memakai keluarga path yang sama (`authorization.oauth2`, `token.oauth2`, `revoke_token.oauth2`) di bawah base `/<tenant>/as/` ([Infor CRM ION API file](https://docs.infor.com/crm/9.2.x/en-us/webclient/upi1639111995644.html)). Keycloak, Entra ID, Okta, dan Auth0 memakai bentuk path yang berbeda. Kesimpulannya: authorization server Infor **sangat mungkin berbasis PingFederate, tetapi ini belum dikonfirmasi**. Tidak ada dokumen Infor atau Ping yang menyatakannya. Nama resmi yang dipakai Infor adalah "InforSTS", "Infor Federation Services (IFS)", dan "Portal Federation Hub" ([Infor Developer Portal](https://developer.infor.com/?p=1692)). Ketidakpastian lain yang perlu dicatat: tidak terlihat `nonce`, tetapi URL yang diamati terpotong sehingga ketiadaannya tidak pasti, dan untuk code flow `nonce` memang opsional. Arti `/v2/` di path portal juga tidak terdokumentasi.

## Tujuh langkah dari klik sampai dashboard, dua di antaranya tak terlihat browser

Inti alurnya: hanya `code` sekali pakai yang pernah lewat browser. ID Token, access token, dan refresh token diambil lewat kanal server-ke-server.

| # | Kejadian | Di mana |
|---|---|---|
| 1 | Browser membuka `mingle-portal/v2/<tenant>`. Tidak ada sesi portal, jadi portal membuat `state` dan `code_verifier`, menyimpannya (cookie atau sesi server), lalu 302 ke `mingle-sso/<tenant>/as/authorization.oauth2?…` | Browser → portal |
| 2 | Jika sudah ada cookie SSO di `mingle-sso`, layar login dilewati. Jika belum, AS menampilkan halaman login Infor atau meneruskan ke IdP pelanggan (Entra ID, ADFS, Okta, Google; SAML 2.0 atau OIDC) ([Infor tutorial ADFS](https://developer.infor.com/tutorials/security-and-user-management/cloud-portal-saml-federation-with-adfs-identity-provider); [Infor OS – Azure AD](https://docs.infor.com/inforos/2026.x/en-us/useradminlib_cloud/inforoscsfcg/lgs1654279533706.html)) | Browser → AS (→ IdP pelanggan) |
| 3 | IdP pelanggan menjalankan login dan MFA-nya, lalu mengirim assertion/token kembali ke hub. Pada kasus federasi ada **dua lompatan protokol bertingkat**, sehingga browser bisa melihat redirect tambahan, misalnya ke `login.microsoftonline.com` | IdP → hub |
| 4 | AS menyetel cookie SSO-nya, menerbitkan `code`, lalu 302 ke `mingle-portal/sso/callback?code=…&state=…` | AS → browser → portal |
| 5 | Portal mencocokkan `state` dengan sesi, lalu **POST back-channel** `code` + `code_verifier` + autentikasi client ke `/<tenant>/as/token.oauth2` ([RFC 6749 §4.1.3](https://www.rfc-editor.org/rfc/rfc6749#section-4.1.3); [PingFederate token endpoint](https://docs.pingidentity.com/pingfederate/12.1/developers_reference_guide/pf_token_endpoint.html)) | Server → server |
| 6 | Portal memvalidasi ID Token (issuer, audience, tanda tangan, kedaluwarsa) ([OIDC Core §3.1.3.7](https://openid.net/specs/openid-connect-core-1_0.html)), memetakan user, membuat cookie sesi portal sendiri, lalu 302 ke deep link asal | Server portal |
| 7 | Aplikasi CloudSuite lain memakai ulang sesi AS tanpa meminta kredensial lagi ([Infor Developer Portal](https://developer.infor.com/?p=1692)) | Browser → aplikasi lain |

Pemisahan domain inilah alasan arsitektural sebenarnya. Satu sesi login, satu konfigurasi federasi per tenant, satu kebijakan MFA, satu penerbit token, dan satu set kunci melayani semua aplikasi Infor dan pihak ketiga. API Gateway ION juga memakai AS per tenant yang sama untuk token mesin ([Infor OS 2026.10 – Gateway token](https://docs.infor.com/inforos/2026.10/en-us/useradminlib_cloud/apigatewayag_cloud/wxo1761727799964.html)). Infor sendiri menyebut manfaatnya "keamanan yang lebih baik lewat autentikasi terpusat" dan "pengelolaan akses yang efisien dengan SSO" ([Infor ADFS tutorial](https://developer.infor.com/tutorials/security-and-user-management/cloud-portal-saml-federation-with-adfs-identity-provider)). Artinya, URL panjang adalah **efek samping** dari skala multi-aplikasi dan multi-tenant. Itu bukan tujuannya.

## Panjang URL tidak menambah keamanan, dan di monolit ancamannya memang tidak ada

Panjang URL Infor sepenuhnya bisa dijelaskan oleh entropi dan encoding. RFC 6749 §10.10 mewajibkan peluang menebak kredensial yang dibangkitkan ≤ 2^-128, dan sebaiknya ≤ 2^-160 ([RFC 6749 §10.10](https://www.rfc-editor.org/rfc/rfc6749#section-10.10)). RFC 7636 §7.1 menyarankan verifier 32 oktet acak, yang setelah base64url menjadi 43 karakter ([RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)). Pengamat yang melihat URL itu hanya mendapat tenant ID, region, client ID, dan `state`/challenge sekali pakai, dan tidak satu pun bisa dipakai untuk login. RFC 9700 malah mengingatkan bahwa nilai di URL bisa bocor lewat Referer, history, dan log (§4.2, §4.3). Itulah sebabnya OAuth hanya menaruh nilai non-rahasia atau sekali pakai di URL ([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)).

Pertanyaan yang lebih tajam adalah ancaman apa yang dijawab tiap parameter, dan apakah ancaman itu ada di ADASI. Semua katalog ancaman RFC 9700 (validasi redirect URI, kebocoran Referer, mix-up, injeksi code, CSRF pada endpoint redirect, PKCE downgrade, open redirect) mengasumsikan ada pertukaran redirect antara client dan authorization server yang **berbeda**. Monolit Laravel dengan form POST same-origin dan cookie sesi tidak punya authorization code, tidak punya callback, dan tidak punya token yang bisa dicegat.

| Parameter OAuth | Ancaman yang dijawab | Ada di login ADASI? | Kontrol setara yang sudah ada di repo |
|---|---|---|---|
| `state` | CSRF / login-CSRF pada callback | Sebagian: login-CSRF ada | Token CSRF Laravel di POST `/login`; state MFA tertunda terikat sesi |
| PKCE | Penukaran authorization code curian | Tidak: tidak ada code | — |
| `nonce` | Replay/injeksi ID Token | Tidak: tidak ada ID Token | — |
| `redirect_uri` eksak | Eksfiltrasi code lewat redirect | Analog: open redirect lewat URL `intended` | `TwoFactorService::safeIntendedUrl()` menolak host/scheme/port asing dan URL `//` |
| `prompt` / `max_age` | Negosiasi kesegaran autentikasi | Analog: step-up | Middleware `password.confirm` |

Dalam praktik, login ADASI yang terlihat di repo justru sudah menerapkan kontrol yang dianggap penting oleh OWASP dan NIST. Ada limiter per akun yang **diagregasi lintas IP** (5 percobaan per 15 menit), limiter per IP dan per subnet /24, tarpit pada cabang gagal, deteksi banyak email berbeda dari satu IP, rem kecepatan global yang memaksa Turnstile, dan *dummy bcrypt hash* agar waktu respons tidak membocorkan apakah email terdaftar (diinspeksi: `config/auth_security.php`). Ada juga event `new_device_login` lewat `CompleteLoginService`, serta `Referrer-Policy: strict-origin-when-cross-origin` di `AddSecurityHeaders`. OWASP Authentication Cheat Sheet bahkan tidak menyebut URL login tersembunyi sebagai kontrol. Yang disebut adalah penghitung gagal per akun, pesan error generik, blokir password bocor, dan MFA sebagai "pertahanan terbaik sejauh ini" ([OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)). ASVS 5.0 bab V6 juga tidak punya persyaratan soal kerahasiaan URL ([OWASP ASVS 5.0 V6](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x15-V6-Authentication.md)).

Jadi, bisakah URL login *terlihat* panjang tanpa integrasi pihak ketiga tetapi tetap memberi manfaat? Jawaban jujurnya: **panjangnya tidak pernah menjadi sumber manfaat**. Ada tiga cara membuatnya panjang, dan nilainya menurun berurutan. Pertama, Passport dipasang di aplikasi yang sama dengan portal sebagai client first-party. URL OAuth sungguhan akan muncul, tetapi IdP dan client berbagi codebase, database, dan session store, sehingga hampir tidak menambah keamanan selama belum ada aplikasi lain yang ikut menjadi client. Kedua, "login transaction ID" di URL (`/login?challenge=<acak>`) memberi manfaat nyata: pengikatan per percobaan, kedaluwarsa, benar saat beberapa tab terbuka, dan korelasi telemetri. Tetapi manfaat itu tetap ada, dan lebih aman, bila ID disimpan di hidden field yang dicocokkan dengan sesi. Ketiga, parameter kosmetik acak hanya menambah risiko. Penelitian Google (CHI 2020) menemukan bahwa hanya nama domain lengkap yang memberi informasi identitas yang tak bisa dipalsukan, dan peserta hanya mengenali **rata-rata 58% URL** ketika teknik obfuskasi dipakai ([Google Research](https://research.google/pubs/measuring-identity-confusion-with-uniform-resource-locators/)). URL login yang panjang dan berubah-ubah menghapus pola stabil yang bisa diajarkan ke supplier ("masukkan password hanya di `portal.<perusahaan>/login`"). URL itu juga merusak bookmark bila memuat nilai kedaluwarsa, dan memperbesar permukaan kebocoran di log dan history ([OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)). Portal besar pun, termasuk Infor, tetap memakai URL masuk yang pendek dan stabil. URL panjang hanya muncul sesaat sebagai redirect internal.

## Lima jalur self-hosted, dan kenapa semuanya memindahkan masalah ke migrasi

Jika ADASI tetap ingin alur seperti Infor (authorization server terpisah dan callback `?code=…&state=…`), semua opsi di bawah menghasilkan URL berbentuk sama, karena code + PKCE memang menaruh parameternya di query string. Perbedaannya ada pada kelengkapan, footprint, dan seberapa banyak fitur keamanan yang sudah dibangun ADASI ikut terlempar.

| Opsi | Kelebihan | Kekurangan / risiko | Cocok untuk ADASI? |
|---|---|---|---|
| **Laravel Passport + add-on OIDC** | Tetap PHP/MySQL. PKCE didukung bawaan (`passport:client --public`, S256), juga `prompt=login` ([Laravel 12.x Passport](https://laravel.com/docs/12.x/passport)). Add-on `jeremy379/laravel-openid-connect` (MIT, Laravel 12) menambah `id_token`, `nonce`, discovery, dan JWKS ([GitHub](https://github.com/jeremy379/laravel-openid-connect)) | Dokumentasi Passport **tidak menyebut OIDC sama sekali**. README add-on tidak menyebut end_session/logout. Default masa berlaku access token **satu tahun**. Tidak ada add-on yang tersertifikasi OpenID. Tim menanggung keamanan IdP rakitan sendiri. Alternatif add-on (`admin9/laravel-oidc-server`, dll.) belum diverifikasi pemeliharaannya | Paling murah. Bermakna hanya bila dipisah ke host `auth.` **dan** ada client lain |
| **Ory Hydra + UI login Laravel yang ada** | Apache-2.0, **OpenID Certified**, headless, tanpa manajemen user. Mendukung MySQL ([ory/hydra](https://github.com/ory/hydra)). Halaman login, google2fa, Turnstile, rate limit, known devices, dan audit tetap di Laravel | Kerja integrasi ke admin API Hydra (endpoint login/consent). Ada binary Go baru yang harus dioperasikan. Path endpoint `/oauth2/auth` belum diverifikasi | **Terbaik bila suatu saat butuh IdP** sambil mempertahankan kontrol yang ada |
| **Keycloak** | Paling lengkap: realm, OTP/WebAuthn, admin console, RP-initiated logout. Termasuk sedikit IdP lengkap yang mendukung MySQL/MariaDB ([Keycloak containers](https://www.keycloak.org/server/containers)). Client Laravel tinggal `socialiteproviders/keycloak` ([SocialiteProviders](https://socialiteproviders.com/Keycloak/)) | JVM sekitar 1–2 GB ("2 GB untuk produksi kecil"). Impor hash bcrypt **tidak jelas**: forum menyebut butuh plugin atau User Storage SPI, sementara satu vendor mengklaim didukung native ([Keycloak forum](https://forum.keycloak.org/t/mysql-user-migration-with-bcrypt-hashing/15345); [Skycloak](https://skycloak.io/blog/migrate-auth0-to-keycloak-step-by-step/)). Untuk satu aplikasi dengan satu client, manfaat SSO-nya nol ([DEV: Intro to Keycloak](https://dev.to/jankaritech/introduction-to-keycloak-5803)) | Hanya bila ADASI membutuhkan SSO perusahaan yang sesungguhnya |
| **authentik** | Python, ada proxy outpost untuk aplikasi tanpa login. Redis dihapus sejak 2025.10 ([release notes](https://docs.goauthentik.io/releases/2025.10/)) | Wajib PostgreSQL (database baru), minimal 2 core / 2 GB ([docs](https://docs.goauthentik.io/install-config/install/docker-compose/)). Klaim CPU per login (~1,2 s vs 72 ms Keycloak) hanya dari cuplikan pencarian, **belum diverifikasi**. Lisensi MIT/enterprise belum dicek di sumber primer | Kurang cocok: menambah stack Postgres |
| **Zitadel** | Go, modern | AGPL-3.0 sejak v3 (netral untuk pemakaian internal tanpa modifikasi) ([Zitadel v3](https://zitadel.com/blog/zitadel-v3-announcement)). Stack v4 berisi 4 container dan PostgreSQL. Hashing password butuh sekitar 4 core ([SSD Nodes](https://www.ssdnodes.com/learn/keycloak-vs-authentik-vs-zitadel)) | Kurang cocok: footprint dan database baru |

Membangun OAuth/OIDC dari nol tidak masuk daftar. RFC 9700 dan OWASP mendaftar puluhan kontrol wajib: PKCE per transaksi, penolakan PKCE downgrade, larangan open redirector, pertahanan mix-up, pembatasan audience, rotasi refresh token, dan seterusnya. Setiap kontrol itu adalah titik kegagalan bagi implementasi buatan sendiri ([OWASP OAuth2 Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html); [RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700)).

Risiko migrasi yang **khusus proyek ini** lebih menentukan daripada pilihan produknya. Semua fitur keamanan ADASI hidup di alur login saat ini: google2fa dan recovery code, Turnstile, limiter identitas, known devices, `auth_audit_logs`, revokasi sesi dan session version, `password.confirm`, kewajiban mengganti password sementara, serta gerbang `is_active` + `account_status = ACTIVE`. Dengan Keycloak, authentik, atau Zitadel, semuanya harus dipindah atau dibangun ulang. Secret TOTP harus diekspor dan diimpor lewat admin API (atau user dipaksa enroll ulang), impor bcrypt `$2y$` belum pasti, dan alur `forgot-password` berbantuan serta SMTP ikut pindah. Hydra atau Passport mempertahankan semua itu karena tabel `users` dan controller-nya tetap. Apa pun pilihannya, otorisasi **tetap di portal**: `users.role`, `supplier_scopes`, `RoleMiddleware`, `EnforceSupplierDomain`, dan policy harus diperiksa ulang setelah callback, dan `is_active`/`ACTIVE` dicek ulang pada setiap login SSO agar supplier yang aktif di IdP tetapi masih PENDING di portal tidak bisa masuk. Registrasi supplier publik (`supplier/registration/*` dengan access key) tetap di portal, dan approval perlu langkah provisioning ke IdP. Muncul juga **dua sesi** (sesi SSO IdP dan sesi Laravel). Tanpa back-channel logout, sesi portal yang dicabut lewat `logout-other-devices` bisa login ulang diam-diam memakai sesi IdP yang masih hidup. Opsi produk berbeda di sini: Authelia, misalnya, tidak mendukung RP-initiated, front-channel, maupun back-channel logout ([Authelia OIDC](https://www.authelia.com/integration/openid-connect/introduction/)). Terakhir, seluruh `tests/Feature/Auth/` butuh fake SSO, dan dev di Laragon butuh Docker atau JVM.

## Prioritas yang benar-benar menaikkan keamanan tanpa IdP

NIST SP 800-63B-4 menetapkan bahwa pada AAL2 verifier "SHALL offer at least one phishing-resistant authentication option", dan OTP yang diketik manual **tidak** memenuhi syarat itu ([NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)). Itu titik lemah terbesar ADASI saat ini: TOTP bisa diteruskan oleh phishing proxy real-time, sedangkan passkey terikat ke domain sehingga domain tiruan tidak bisa memakainya ([Laragear/WebAuthn](https://github.com/Laragear/WebAuthn)). Di repo juga ada temuan konkret: `.env.example` memakai `SESSION_LIFETIME=480` (8 jam idle), sedangkan NIST AAL2 menyarankan inactivity timeout tidak lebih dari 1 jam dan batas absolut tidak lebih dari 24 jam. Nilai produksi yang sebenarnya belum diverifikasi.

| Prioritas | Langkah | Kenapa | Catatan / ketidakpastian |
|---|---|---|---|
| 1 | **Passkey (WebAuthn)** sebagai opsi MFA/primer, diwajibkan atau didorong untuk finance, admin, dan purchasing. TOTP dan recovery code tetap sebagai cadangan | Satu-satunya kontrol di daftar ini yang mematahkan phishing proxy. Berjalan in-process, tanpa layanan eksternal | Laragear/WebAuthn **sudah diarsipkan** dan menunjuk ke `laravel/passkeys`. Status resmi `laravel/passkeys` **belum terkonfirmasi**: hanya ada listing direktori pihak ketiga (v0.2.1, pra-1.0) ([laraplugins.io](https://laraplugins.io/plugins/laravel/passkeys)). `spatie/laravel-passkeys` lebih matang tetapi berorientasi Livewire ([Spatie](https://spatie.be/blog/a-package-to-handle-passkeys-in-laravel)). Verifikasi di Packagist sebelum memilih |
| 2 | **Idle dan absolute timeout** yang dibedakan per role (misalnya ≤1 jam idle untuk finance/admin), regenerasi sesi saat ganti scope/konteks supplier, pertimbangkan nama cookie `__Host-` | Selisih 8 jam vs ≤1 jam terhadap NIST AAL2. OWASP menyebut 2–5 menit untuk aplikasi bernilai tinggi ([OWASP Session](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)) | Nilai produksi belum diverifikasi |
| 3 | **Notifikasi email event keamanan**: perangkat baru (kini hanya in-app), ganti password, aktif/nonaktif MFA, recovery code dipakai, lockout berulang. Sertakan tautan "bukan saya" berupa `temporarySignedRoute` untuk mencabut sesi ([Laravel URL Generation](https://laravel.com/docs/12.x/urls)) | ASVS 6.3.5/6.3.7. Supplier mendeteksi pengambilalihan akun lebih cepat | Session versioning sudah ada, jadi pencabutan tinggal disambungkan |
| 4 | **Cek password bocor offline** bila "tanpa pihak ketiga" adalah syarat keras | **Saat ini repo sudah memanggil pihak ketiga**: `AuthSecurityServiceProvider` menyalakan `Password::uncompromised(3)` di produksi, dan itu memanggil API haveibeenpwned.com (k-anonymity) ([Laravel Validation](https://laravel.com/docs/12.x/validation)) | Pengganti: blocklist top-N lokal (ASVS L1: 3.000) atau Bloom filter sekitar 0,5 GB dari dataset `PwnedPasswordsDownloader` ([HIBP](https://github.com/HaveIBeenPwned/PwnedPasswordsDownloader)). Registrasi supplier sengaja tanpa cek ini; mengubahnya adalah keputusan bisnis |
| 5 | **Login attempt ID di hidden field**, bukan di URL: ID acak yang dicocokkan dengan sesi, sekali pakai, berkedaluwarsa, dan dicatat di audit | Manfaat `state` tanpa kebocoran URL: aman dengan banyak tab (kunci sesi tunggal saat ini tertimpa oleh percobaan kedua) dan funnel telemetri (password OK → MFA gagal → selesai/ditinggal) | Pemeriksaan `started_at` di `mfa.pending` sudah merupakan implementasi parsial |
| 6 | **Step-up dan tes tepi redirect**: pastikan perubahan rekening, payee, dan finalisasi DRP berada di balik `password.confirm` (nanti juga asersi passkey). Tambahkan tes `safeIntendedUrl()` untuk `/\evil.com`, `%2F%2F`, `https://host@evil`, dan scheme campuran huruf besar/kecil | Menjaga analog `redirect_uri` dan `max_age` di monolit ([OWASP Redirects](https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html)) | Cakupan route sensitif belum diaudit |
| Tunda | **IdP terpisah** (Hydra lebih dulu, Keycloak bila butuh SSO perusahaan penuh) | Layak hanya bila ada pemicu: staf login dengan Entra ID/direktori korporat, aplikasi internal kedua atau ketiga butuh SSO, client mobile/API, atau auditor menuntut MFA terpusat | Supplier eksternal tetap butuh akun lokal atau federasi B2B; review registrasi tidak hilang |

Satu aturan UX melengkapi semuanya: terbitkan **satu URL masuk kanonik yang pendek** di domain perusahaan sendiri, tanpa query parameter yang terlihat user di halaman auth, dan pakai domain yang sama di setiap email sistem. Supplier jadi bisa mempelajari satu pola, sementara passkey menghapus kebutuhan menilai URL sama sekali karena browser yang menegakkan origin.

## Kesimpulan

Pertanyaan "bisakah login kita terlihat seperti Infor" ternyata salah sasaran. URL Infor adalah tanda bahwa identitas sudah dipisahkan menjadi layanan bersama untuk ribuan tenant dan puluhan aplikasi. Meniru tandanya tanpa memiliki kebutuhan itu hanya memindahkan kompleksitas tanpa memindahkan manfaat. Untuk ADASI, celah yang tersisa bukan di bentuk URL. Celahnya ada pada faktor kedua yang masih bisa di-phish, sesi yang hidup terlalu lama untuk role yang memegang data pembayaran, dan sinyal pengambilalihan akun yang belum sampai ke inbox pemilik akun.

Ada satu ironi kecil yang layak dicatat. Kriteria "tanpa pihak ketiga" sudah dilanggar oleh kode yang ada lewat panggilan HIBP. Sebaliknya, kontrol keamanan terkuat yang tersedia, yaitu WebAuthn, justru sepenuhnya lokal. Bila suatu hari IdP memang dibutuhkan, jalur paling murah risiko adalah Hydra di depan layar login Laravel yang sudah ada. Pilihan itu sebaiknya diambil karena ada aplikasi kedua yang perlu login, bukan karena URL-nya ingin terlihat panjang.
